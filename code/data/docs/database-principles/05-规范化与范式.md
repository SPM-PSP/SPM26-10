# 规范化与范式

## 1. 为什么要规范化
数据库设计不合理时，可能出现：
- 数据冗余
- 更新异常
- 插入异常
- 删除异常

规范化的目标是减少冗余，提升结构合理性。

## 2. 函数依赖
若在关系中，属性组 X 的值唯一确定属性组 Y 的值，则称 Y 函数依赖于 X，记作：

`X -> Y`

## 3. 候选码与主属性
- 候选码：能唯一标识元组的最小属性集
- 主属性：属于某个候选码的属性
- 非主属性：不属于任何候选码的属性

## 4. 第一范式 1NF
关系中的每个属性值必须是不可再分的原子值。

违反 1NF 的常见情况：
- 一个字段中存放多个值
- 一个单元格中嵌套列表

## 5. 第二范式 2NF
在 1NF 基础上，所有非主属性必须完全函数依赖于候选码，不能只依赖候选码的一部分。

它主要用于消除对复合主键的部分依赖。

## 6. 第三范式 3NF
在 2NF 基础上，非主属性不能传递依赖于候选码。

也就是说，非主属性之间不应形成“间接决定”关系。

## 7. BCNF
若关系中每个决定因素都包含候选码，则该关系属于 BCNF。

BCNF 比 3NF 更严格。

## 8. 规范化例子
假设有关系：

`StudentCourse(Sno, Sname, Cno, Cname, Teacher, Grade)`

问题：
- 学生姓名依赖于 Sno
- 课程名和教师依赖于 Cno
- 成绩依赖于 (Sno, Cno)

这说明多个概念被混在一张表中，容易产生冗余和异常。

规范化后可拆成：
- Student(Sno, Sname)
- Course(Cno, Cname, Teacher)
- SC(Sno, Cno, Grade)

## 9. 规范化与性能
规范化有利于结构清晰和一致性控制，但过度拆分可能带来更多连接操作。

实际工程中常在规范化与性能之间平衡，有时会适度反规范化。
